**Ruling 15 pipeline (Divit 2026-10-13): if the spec has `"pipeline": "r15"` (built by `ops/skeleton.py build`), these steps replace 1-8 below.**
- Read `.cache/packs/<slug>.r15.md` (`python3 ops/skeleton.py pack <url>` writes it). It lists the section order, the 10 FAQ slots (locked questions are fixed by code), the link words per slot, the claims menu with ids, and the prevention instructions with GOOD/BAD examples. Read `docs/PREVENTION.md` once.
- **Code has already built:** the hero default prompt, product name, breadcrumb, explore CTA, the comparison table, the locked FAQ questions (gate-passing AlsoAsked, verbatim, and the default definition and how-to-build), and the link plan. The other FAQ slots are written slots: you write those questions (Divit 2026-10-16). Never edit these. `skeleton.py set` refuses the code-built fields.
- Write `spec.plan` first, as in step 4 below (plan-check must be clean). Then write **prose only, one section at a time** with `python3 ops/skeleton.py set <url> <field> "<text>"` (HTML exactly as the field needs it; JSON for chip_adds, image_brief, domain_sources, claims_used). After each section, run `python3 ops/skeleton.py check <url> <section>`; code autofixes the deterministic rules first. Fix every P0/P1 it lists before the next section. The order is hero, features, why, usecases, howto, faq.
- **Claims:** every sentence about Emergent maps to a claim id in the pack's menu, listed in `claims_used`. Every fact about a third party, a law or a standard has a `domain_sources` entry `{claim, source_url, date, quote}`, where `quote` is the exact span from the source that states it (6+ words). No span, no claim: cut it.
- **FAQ:** `python3 ops/skeleton.py answer <url> <n> "<answer>"` for each slot. For a written slot, also pass `--q "<question>"`: a question a real person building this asks, plain, specific and useful, about this page's topic (never hub-level generic), working in the suggested secondary naturally (at most one secondary per question), builder intent, no state-specific, legal, medical or financial advice, no brand and no other company's pricing, never another page's primary or the same intent as another question. The command gates it (PA3-PA21) and refuses a reject: rephrase, never argue. Answers stay answer-first, truthful and sourced. Where the pack gives link words, write those words in the answer; code makes them the link. Then `python3 ops/skeleton.py assemble <url>` and `python3 ops/skeleton.py check <url> faq`.
- **Quiz pages** (SurveyQuiz slug containing "quiz"; the pack has a Quiz section): write the playable quiz JSON per `docs/QUIZ.md` (6-10 questions, sourced facts or `derivable` working, results that deliver the H1's promise, never a diagnosis), save it to your folder, `python3 ops/skeleton.py set <url> quiz @<file>.json`, then `python3 ops/skeleton.py check <url> quiz` to 0 (QC Z codes; `hubctl sources-check <url>` covers the quiz sources).
- Finish with `python3 ops/skeleton.py check <url> all` at 0, then `python3 ops/hubctl.py qc <url> --stamp`, `python3 ops/hubctl.py state <url> qc_pass --by <your id>`. Return: first-run result per section (P0/P1 count before your fixes), and the H1 and meta title.

You write exactly one child page, given its URL. Work in the repo root. On macOS use `.venv/bin/python3` wherever these steps say `python3`. The standard is a senior human writer's: never let the page read as AI-written (`rules/HUB_RULES.md` 2b).
1. People Also Ask comes from AlsoAsked (DataForSEO retired, Divit 2026-10-10; no live SERP pull). If the page has no pull yet (QC F1), the orchestrator runs it (weekend: `weekend.py aa <url>`, 1 credit); then `python3 ops/hubctl.py paa <url>` gates the candidates. Keyword ideas are the page's secondaries from the Semrush workbook; top-10 and intent context come from the brief (Semrush workbook and Wave 3 SERP data).
2. `python3 ops/hubctl.py pack <url> --role writer` and read the pack it writes (brief, the rules you need, a one-line defect catalogue, the hub exemplar excerpt, the image brief guide). Read it instead of the full rulebook; open a full rules file only for a detail the pack does not cover. Match the exemplar's standard, never its words.
3. `python3 ops/hubctl.py init <url> --by <your id>` if the spec does not exist; otherwise continue it (it may be a rework with notes in `status/` and the spec's `review` record).
4. **Plan before prose** (`rules/HUB_RULES.md` 8). Write `spec.plan` first: `angle` (how this page wins against the top 10), `tab_stories` (four distinct one-sentence stories), `openers` (planned paragraph openers that start differently), `heading_shapes` (four tab H3 shapes, different from each other and from sibling pages), `claims_to_source` (every claim about third-party systems, legal or professional terms, or best practice). Run `python3 ops/hubctl.py plan-check <url>` and resolve every warning before writing copy.
5. **Verify domain claims as you write, sparingly.** At most 8 sources per page (QC P4). Check each claim in `plan.claims_to_source` with a web search (load WebSearch through ToolSearch if deferred); a search snippet from the primary source is enough when it states the claim, so fetch a full page only when the snippet does not. Record `{"claim", "source_url", "date"}` in `spec.domain_sources`, then run `python3 ops/hubctl.py sources-check <url>` (the automated link check; QC P3 blocks dead or moved sources). A claim you cannot source comes out of the copy, or becomes a plain instruction with no claim about the world.
6. Write every field per `rules/HUB_RULES.md`, after reading `rules/CONTENT_DEFECTS.md`. The FAQ has exactly 10 items, each an on-topic question: the gate-passing AlsoAsked questions first, verbatim, then questions you write (Divit 2026-10-16; `skeleton.py assemble` records each in `faq_sources` as paa or written; never pad with drift, forced keywords or hub-generic questions), carries at least 6 secondaries where they read naturally (all of a secondary's words in one sentence, any order; never force an exact string), and links: the hub in item 2 plus 2-3 related pages with exact-match anchors. List every Emergent capability the page relies on in `claims_used` (ids from `rules/capabilities.json`; a needed capability that is not approved goes to the orchestrator, never into the copy). Any third-party fact or statistic in prose must match `rules/facts.json` or be removed. Generate the comparison table with `hubctl table` from the library; write the `image_brief` per `docs/IMAGE_BRIEF.md`, including a `story` list on every tab that ties the tab copy to the image. Build the FAQ and mockup embeds in Python so quoting is exact. FAQ questions never name a brand or product (gate PA14) or ask for a file format or download (PA15); the hero description follows QC D1 (at most 130 characters, primary keyword, leads with what the visitor gets, plain words) and the how-to description QC D2 (one sentence, at most 140 characters, primary keyword, says what the steps achieve) (Divit, 2026-10-09; rules/HUB_RULES.md section 5). The explore CTA is at most 34 characters (QC D3, P1, Divit 2026-10-10): shorten the display name, never the verb. From batch 2 onward, 2-3 general FAQ answers (items 3-10) each carry one subtle sentence on the question-specific Emergent moat, claims from rules/claims.json only, no hard sell, no competitor names (QC F9).
7. `python3 ops/hubctl.py qc <url>`; fix root causes until TOTAL = 0. Never weaken a rule. QC reports every instance of a craft defect (Q5-Q8) and every story mismatch (I4); fix all of them, not the first.
8. `python3 ops/hubctl.py state <url> qc_pass --by <your id>` (recorded, so no reviewer who wrote the page can judge it). After a rework, the orchestrator re-renders and runs `hubctl ready`. Return a 3-line summary: H1, meta title, any P2 you accepted and why.

**Rework (one per page): blocking findings only.** Fix every blocking finding in `review.findings`; never edit for a note. There is no second review: after your rework the page goes to Divit, so QC to zero and leave nothing half-fixed (notes go to the proposed-rules queue for Divit). Re-source only the claims a blocking finding names; liveness is the link check, not you. **Fix the defect class, not the instance.** A note names one example of a kind of defect (a tacked-on ", so" ending, a phrase repeated in two fields, an FAQ answer that restates the body, a number that disagrees between copy and image). Before changing anything, search the whole page, every field, the FAQ and the image brief, for every occurrence of that class, and fix them all. Rewrites create new instances, so search again after rewriting. A note fixed in one place and left in another is a failed rework.

Keep temp files in your own folder, named after your writer id (for example `<scratchpad>/<writer id>/`), never in a shared folder: parallel writers once overwrote each other's scripts. Do not touch Webflow, other pages, shared code or rules.
